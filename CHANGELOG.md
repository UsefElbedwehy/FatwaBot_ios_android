### 2026-07-11 — On-device feedback round: location/notification hang, premium onboarding + Worship + Settings redesign
- **iOS location-permission hang (root cause of both "location stuck" and "notification stuck" reports)** — `SystemLocationProvider.resolve()`'s `.notDetermined` case called `requestWhenInUseAuthorization()` then immediately fell through into `requestLocation()` before the OS dialog was answered; `requestLocation()` is a no-op pre-authorization, and the delegate's `locationManagerDidChangeAuthorization` never retried it after the user actually granted access — the continuation never resumed, hanging forever. Since Home's `.task` chain awaits location resolution alongside notification-permission request and config refresh sequentially, a stuck location resolve could present as "everything on the home screen is stuck." Fixed by tracking `awaitingAuthorization` and only calling `requestLocation()` once the delegate reports an actual authorized/denied outcome. Android's permission flow (UI-layer `ActivityResultContracts` launchers) was independently verified to not have this bug — no Android change needed.
- **Full-width, larger-padding buttons** for better tap targets — iOS onboarding buttons gained `.frame(maxWidth: .infinity)` + `.controlSize(.large)`; Android's onboarding buttons already used `fillMaxWidth()` but gained explicit `contentPadding(vertical = 16.dp)` to match.
- **Islamic "mihrab arch" motif in onboarding** — the pointed-arch shape specified in `docs/05_DESIGN_DIRECTION.md` since M0 but never implemented: new `MihrabArchShape`/`ArchIconBadge` (iOS, `DesignSystemKit`) and `mihrabArchPath`/`ArchIconBadge` (Android, `:core:designsystem`, `Shape` via `Path`) replace bare SF Symbol/Material icons in onboarding's Welcome/Highlights/Priming steps on both platforms.
- **Settings → Profile-first redesign** (stakeholder direction: "we will add login for sure and we need to add more things here") — both platforms gained a profile header section (avatar circle, "Guest", "Sign in — coming soon") above the existing settings content. The sign-in row is intentionally inert, not a fake-functional button — no real login exists yet (blocked on Q8 backend credentials). Android's Settings tab previously had **no real screen at all** (generic `ComingSoon` placeholder) — this is Android's first real Settings implementation, wired into `RootScaffold`.
- **Worship tab: list → premium grid redesign** ("worship design is not premium at all, make it grids of squares and amazing icons") — both platforms replaced the flat list of `NavigationLink`/`ListItem` rows with a 2-column grid of square tiles: filled icon in a rounded `primaryContainer` badge over a `surfaceElevated`/`surfaceContainer` card.
- **Prayer countdown Live Activity: on by default** (iOS-only, ADR-0016 originally specified off-by-default) — `UserDefaultsLiveActivityPreferenceStore` now registers a default of `true` via `UserDefaults.register(defaults:)`, while an explicit user opt-out is still respected. No Android equivalent exists (no Live Activity feature on Android).
- Verified with real builds + full test suites on both platforms: `swift test` (83 tests) + full `xcodebuild` app-target build, all green on iOS; `./gradlew test` + `:app:assembleDebug` (960 tasks), all green on Android.

### 2026-07-08 — M4: iOS Live Activity — prayer countdown (ADR-0016)
- **New `FatwaBotLiveActivity` app-extension target** (`ios/LiveActivity/`), added alongside the existing `FatwaBotWidgets` extension per ADR-0016 — local-only ActivityKit, zero push/APNs. Renders the countdown to the next prayer on the Lock Screen and in the Dynamic Island (expanded, compact, and minimal presentations) via `Text(timerInterval:)`, which the system animates client-side with no app wake-ups between updates.
- **`PrayerActivityAttributes`** (PrayerKit, `#if canImport(ActivityKit) && os(iOS)`-guarded since ActivityKit isn't available on the plain-macOS platform these packages also target for `swift test`): static `locationName` attribute + a `ContentState` of exactly `{ prayerName, prayerTime }`, per the ADR.
- **`PrayerLiveActivityManaging` boundary** (PrayerFeature, mirrors the existing `HeadingProviding`/`#if canImport` seam in `QiblaScreen`) keeps `PrayerViewModel` and its unit tests free of any ActivityKit dependency; `SystemPrayerLiveActivityManager` is the real iOS-only implementation, wired in only by `AppContainer`.
- **Opt-in, off by default** (`UserDefaultsLiveActivityPreferenceStore` — `UserDefaults.bool(forKey:)` returns `false` when unset, so no explicit default-registration needed): the Settings tab — previously a bare "coming soon" placeholder with zero real content — gained its first real screen, a single toggle. Disabling ends the activity immediately rather than waiting for the next state transition to notice.
- **`PrayerViewModel` wiring**: `apply(location:)` and `refreshNextPrayer()` (already-existing state-transition hooks — a new "next prayer" resolved, or a timer-tick/foreground refresh) now also sync the Live Activity when enabled, mirroring exactly the widget-snapshot update pattern from task 42 (skipped on the synchronous cold-start init path for the same reason: it's a system-IPC side effect, not needed to unblock first paint, and the async `start()` re-apply moments later still updates it).
- **Simplification vs. the ADR's literal wording on "explicitly ends it at local midnight":** there's no existing day-boundary/midnight timer in `PrayerViewModel` to hook an explicit `end()` call into (the ADR's phrasing assumed one existed). Since `apply()`/`refreshNextPrayer()` already re-sync the activity to whatever the *current* next-prayer state is on every foreground/tick, a day boundary is naturally handled the same way — the activity just starts reflecting tomorrow's Fajr once the app re-enters and recomputes, same as `today`/`tomorrow` do today. `ActivityKit`'s own `staleDate` (30 min after the countdown target) remains the safety net for the case where the app never re-enters before the target passes.
- New tests assert: off by default; enabling starts the activity with the current next-prayer; disabling ends it immediately; a `refreshNextPrayer()` tick also re-syncs while enabled. (Testing a fire-and-forget `Task {}` launched from `@MainActor` code needed a small polling `waitUntil` helper rather than a single `Task.yield()` — one yield doesn't reliably let the spawned task complete before assertions run, which showed up as session-run-to-run test flakiness before the fix.)
- Verified with real builds: `swift test` (82 tests, stable across repeated runs) + full `xcodebuild` app-target build, which now also compiles and embeds the new `FatwaBotLiveActivity.appex` into `FatwaBot.app/PlugIns`.

### 2026-07-08 — M4: Performance pass (cold start, widget battery)
- Static-code performance audit (no device/Instruments profiling available in this environment — every finding is a file-verified static analysis, not a runtime trace) on both platforms, independently cross-verified by multiple agent passes plus direct manual reading of the cited files.
- **Fixed on both platforms:** `PrayerViewModel.init`'s cached-location fast-path (the "instant first paint from cache, refine async" pattern) was also synchronously triggering a widget-snapshot write — a second 3-day prayer-timeline recomputation, a disk write to the app-group/shared-prefs container, and a `WidgetCenter.reloadAllTimelines()` / Glance `updateAll()` IPC call — all before the tab bar's first frame. Added an `updateWidget` parameter to `apply(location:)` (default `true`), passed `false` from the synchronous `init` cached-location path only; `start()`'s subsequent async re-apply (which already runs moments later on every launch) still updates the widget normally, so widgets stay just as fresh — the fix only removes this work from the *blocking* part of cold start.
- **Investigated and deliberately left alone** (real but low/negligible-impact — flagged rather than "fixed" to avoid churn/risk for sub-millisecond wins): `ConfigService`/`HomeViewModel`'s eager synchronous config-snapshot file read on first Home-tab construction (both platforms — same architecture, same tiny JSON file, same "offline-first instant-then-refine" pattern already accepted elsewhere), the onboarding-completion-check synchronous file read gating first composition/render (both platforms, sub-100-byte file), and Android's `EncryptedPrefsAuthTokenStore` eager Keystore/`MasterKey` construction (only reached on first Journey-tab visit, not app cold start).
- **Widget battery: no defects found on either platform.** Both `WidgetCenter.reloadAllTimelines()` call sites (iOS) and both `updateAll()` call sites (Android) are gated to once-per-meaningful-change (once per location resolve/settings change for prayer, once per `load()` for gamification), not per state mutation. Android's Glance `updatePeriodMillis` (30 min) is already at the OS-enforced practical floor. All widget `getTimeline`/`provideGlance` implementations on both platforms read only pre-computed snapshot files — zero network or heavy computation in the widget process, as designed since M1/M3.
- New tests on both platforms specifically assert the fixed behavior: cached-location construction does not trigger a widget write/reload, but the subsequent `start()` call still does.
- Verified with real builds + full test suites on both platforms: `swift build` + `swift test` (78 tests) + full `xcodebuild` app-target build, all green on iOS; `./gradlew test` + `:app:assembleDebug` (960 tasks), all green on Android.

### 2026-07-08 — M4: Accessibility audit (VoiceOver/TalkBack, Dynamic Type, reduced motion)
- Ran independent iOS + Android accessibility audits, cross-checked every finding against live file state before acting (both reports were fresh and accurate this time, unlike the stale iOS report earlier in M4's empty-states audit).
- **Reduced motion — the single biggest gap, now fixed on both platforms:** iOS gained a reusable `motionAnimation(_:value:)` view modifier (`DesignSystemKit/ReducedMotion.swift`) that silently skips the animation when `accessibilityReduceMotion` is on; wired into every `MotionTokens`-backed call site plus the two `withAnimation` sites (Qibla compass rotation, Prayer day-navigation) that predated `MotionTokens`. Android had **no reduced-motion signal anywhere in the codebase** — added `LocalReduceMotion`/`rememberReduceMotion()`/`motionAnimationSpec()` (`:core:designsystem`, reads the system's `Settings.Global.ANIMATOR_DURATION_SCALE` "remove animations" setting, the closest Android equivalent to iOS's API), provided once at `AppRoot` so it's available everywhere, and wired into all 5 existing animation call sites (Qibla, Tasbeeh, Azkar, Awrad, Gamification).
- **VoiceOver/TalkBack labels added** for every icon-only interactive control the audits found actually missing one: Prayer's day-navigation chevrons (both platforms), Azkar's translation toggle, Tasbeeh's history button, Dua's favorite/transliteration toggles, Awrad's per-wird increment button, Android's JourneyTab/WorshipTab back arrows. (Several audit-flagged "missing" labels on Android — Awrad's stats/add toolbar buttons — turned out to already be correctly labeled on file-state verification; left untouched.)
- **Composite-row grouping** (`.accessibilityElement(children: .combine)` / `Modifier.semantics(mergeDescendants = true)`) added to the highest-traffic rows so VoiceOver/TalkBack read them as one stop instead of 2-3 disjoint fragments: Prayer's times list, Gamification's streak/mission/badge rows, Leaderboard's board-summary/entry rows and join-dialog switch, Awrad's wird/stat rows, Qibla's static-fallback and accuracy-indicator views, plus Gamification's badge earned/locked state (previously conveyed by icon alone — added an explicit accessibility value on both platforms).
- **Dynamic Type / font-scale safety** on the two fixed-circle tap targets (Tasbeeh, Azkar): iOS uses `@ScaledMetric`/`.minimumScaleFactor`; Android grows the circle by the system font-scale setting (capped at 1.6×) since Compose's `Text` has no direct minimum-scale-factor equivalent in this project's Compose version.
- **Explicitly deferred** (flagged, not silently dropped): a real `error` field surfaced distinctly from "empty" in Azkar/Dua/Hadith/Awrad `UiState` (same gap already deferred from the empty-states audit — same root cause, same fix needed); the long tail of secondary composite rows not on the highest-traffic list (Hadith reading screen's entry-number/benefit-note groupings, Dua/Awrad create-sheet template rows, widget rows); a `SpacingTokens` object (the Android audit noted color/shape/motion tokens exist but spacing doesn't — unrelated to this task's scope, noted for a future design-system pass).
